# 2026-07-16｜先记住，再约束

## 方向纠偏

真实 DeepSeek 试玩暴露了两个问题：Director 容易耗尽结构化输出预算；更重要的是，一句普通的“一起吃饭”被抽成了承诺对象并进入强校验账本。这个结果虽然一致，却没有证明它值得如此重的机制。

叙事失真首先应由记忆和小结解决。承诺、秘密披露、关系、情绪、任务进度和剧情意义都高度依赖语境；在没有长期记忆与长篇失败样本前，为它们建立通用 ID、生命周期、证据门槛、原子状态和分支语义，成本明显高于收益。

因此暂停此前“继续扩建 Director / 承诺账本 / Local Canon”的计划，先缩小默认核心。

## 减负批次 A

本批次从活动运行时删除：

- `commitment`、`commitment_update`、`secret_disclosure` 事实与状态；
- 提交后 Director、DirectorPlan/Beat 及其 DeepSeek 调用；
- Local Canon、generation 原型/预算/过期；
- storylet、effect、任务 flags、通用 state patch 与事实锚点；
- 条件出口、条件场景对象、条件结局；
- world graph 寻路和 `world.step`；
- `facts` CLI 伪记忆入口；
- 相关协议字段、测试、内容契约和活动文档。

活动权威状态现在只有：

```text
positions
item_locations
```

后验抽取只接受人物换场与关键物品转手。代码仍检查作者实体、可见性、可携带性、当前归属、接收者和共处位置。证据文本仅用于审计，不做字符串相等门槛。

## 保留项

- 玩家/NPC 主体感知隔离；
- 自然语言与可编辑行动提案；
- revision-bound FactExtraction / FactBatch；
- 整批原子提交和一次有限重写；
- checkpoint、undo、branch；
- trace 与短期已提交散文；
- 只检查内容引用与物理账本初值的小型校验器。

这些是低耦合、安全收益明确的基础设施，不替作者或模型判断剧情。

## 下一批：记忆与小结

优先做一条可观察、可替换的软记忆管线：

1. 每回合从已提交散文生成事件小结，不写权威状态；
2. 维护开放线程、人物立场/约定、已解决事项和场景变化；
3. 按人物、场景、章节分层压缩；
4. 记忆跟随 checkpoint 与 branch；
5. 旁白和 `ideas` 使用同一份裁剪后记忆上下文；
6. 用多回合试玩测量遗忘、重复、矛盾和 token 成本。

只有记忆仍反复失败、且错误代价足够高的事项，才进入后续硬规则候选。每个候选单独评估，不再预先建立一套包打天下的铁律 DSL。

## 验收

- 活动内容与开放夹具通过新校验器；
- 历史 `pre_pivot_archive` 只识别归档身份，不维护旧 DSL；
- 全量离线测试通过；
- CLI 首回合普通对话不再产生承诺、披露、任务旗标、Director 进场或条件结局；
- `state` 只显示 `positions` 与 `item_locations`。

## M1 已实现：分支内原始记忆

- 新增不可变 `MemoryEvent`：记录回合、commit、玩家原话、散文、场景前后、参与者、引用与物理变化；
- 新增 `MemoryState`，完整保存当前分支事件，并预留滚动小结、开放事项、人物/场景小结和最近解决事项；
- 最近 4 个事件继续进入现有 `PerceptionSnapshot.recent_events`，完整日志不直接塞入 prompt；
- M1 只服务玩家视角，NPC 感知不会复用玩家的最近事件；
- checkpoint 现在保存 `MemoryState`，撤回和分支会同步恢复记忆；
- `memory` 与 `memory raw` 明确以“非权威状态”展示；
- session log 与 trace 随成功提交记录原始记忆事件；
- M1 不调用 DeepSeek，不从散文抽取承诺、关系或任务状态。

## M2 已实现：按需软小结

- 保留最近 4 个原始事件；更早未压缩事件达到 4 个或 2400 字符时触发，一次最多处理 6 个；
- 小结只读取旧 digest、已提交事件和作者人物/场景目录，代码拥有压缩边界；
- DeepSeek 小结使用非思考、低温、800 token JSON 调用，同一回合不做修复重试；mock 提供确定性的离线抽取式实现；
- 小结在玩法提交后执行，成功或失败元数据附着到当前 checkpoint，不增加物理 revision；
- 失败不回滚、不删原始事件，并冷却 3 个回合间隔后再尝试；
- `memory`、session log 与 trace 可观察成功结果或失败原因；
- M2 不向旁白或 `ideas` 注入 digest，这一消费层留给 M3。

## M3 已实现：统一生成上下文

- 新增 revision-bound `MemoryContext`，绑定主体、回合、压缩边界和裁剪元数据；
- 旁白与 `ideas` 使用同一份滚动小结、开放事项、人物/场景笔记和未压缩事件；
- 未压缩缓冲最多 8 条，覆盖首次压缩前第 5–7 回合可能出现的记忆空档；
- 自由文本总预算 4800 字符，超限时确定性裁剪并标记 `truncated`；
- `FactExtractionRequest` 不携带 `MemoryContext`，软小结不能参与物理事实抽取；
- prompt 规定当前感知/事实优先，旧人物不等于当前在场，开放事项不等于已完成；
- 上下文不能跨主体、回合或 revision 使用；NPC 不复用玩家记忆；
- M2 的人物/场景 catalog 同步收窄到压缩边界前玩家亲历过的实体，避免 M3 消费 digest 后出现作者隐藏目录侧漏；
- digest 异常时退回原始事件，小结失败原因不进入 prompt；
- trace 记录旁白和提案实际使用的上下文，便于后续长篇试玩测量遗忘、重复与 token 成本。
