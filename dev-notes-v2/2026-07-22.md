# 2026-07-22｜requires 记账：offered 语义与按需加速

## 背景

霍格沃茨草稿审查暴露了 requires 机制的结构性弱点：`engaged/resolved` 只能由 M2
小结标注，而 M2 是低频批处理（4 回合保护窗 + 攒 4 条触发 + 3 回合冷却），
`requires: resolved` 的链条每层要多等 4-8 回合；且记忆压缩失败会连带卡住剧情
推进——记忆质量和故事进度被耦合在一条不可靠通道上。

否掉的备选：每回合专门状态调用（关键路径成本、逐回合判断收尾不稳）；挂事实
抽取（往物理通道灌叙事语义，违反 7-16 纪律）；旁白散文夹带 JSON（破坏纯文本
散文质量保障）。

## 落地两项

### 1. `requires: offered` 与进度包含语义

- 合法状态增加 `offered`：由代码在候选进 prompt 时即时标记，零时延；
- 满足判定从精确匹配改为**进度包含**（`REQUIRES_SATISFIED_BY`）：
  `offered` 被 offered/engaged/resolved/dropped 满足（"抛出过即可"，前置推进
  后不会反锁后继）；`engaged` 被 engaged/resolved 满足；`resolved`/`dropped`
  精确匹配（dropped 是独立分支，但计入"抛出过"）。

### 2. 按需加速 M2 记账（module_bookkeeping）

- `pending_requires_blockers`：识别"被卡住且唯一原因是前置模块已抛出、状态
  待 M2 判定"的模块（目标 offered 不会 pending——那是代码记的；前置 unseen
  也不会——加速帮不上）；
- `plan_memory_compaction(urgent=)`：有被卡模块时绕过"攒 4 条"批量门槛，
  哪怕只压 1-2 条也跑一次小结；**保护窗（最近 4 条不压）与 3 回合冷却不变**，
  不会产生压缩风暴；
- trigger 记为 `module_bookkeeping`，被卡模块清单随 trace 可查。

效果：requires 链条解锁延迟从固定 4-8 回合降到最多一个冷却周期；mock 下链条
仍需注意（mock 不产 module_updates），试玩用 DeepSeek。

## 四道防线（配合内容侧纪律）

少用（requires 只留后期硬门槛）→ 用轻的（offered）→ 记得快（按需加速）→
记错了能救（后续可加 CLI module set 调试命令，未实现）。

## 同日修复：秘藏物品无法转手（草稿审查问题 A）

霍格沃茨草稿的两件关键物品都是 `visible_when_carried: false`（叙事正确：
贴身秘藏），但铁律的 `physical.item_not_visible` 只认感知可见物品——秘藏
物品永远不在感知里，"携带者当面拿出来交给玩家"这个最正当的流程被挡死，
归属永久冻结。抽取账本同样只列可见物品，隐藏物品连当前归属都不给抽取器。

修复：引入"可转移集合" = 可见物品 ∪ 权威携带者本回合在场的携带物品。
校验与账本两侧同步放宽。防伪造边界不变：归属必须与权威账本完全一致、
携带者必须共处一地；携带者不在场的隐藏物品照旧拒绝。账本只进抽取器，
不进玩家感知，无泄漏面。
