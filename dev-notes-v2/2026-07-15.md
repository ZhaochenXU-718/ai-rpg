## 形成的结论

- 内容文件显式声明 `content_profile`：活动故事使用 `narrative_first`，历史机械样本使用 `pre_pivot_archive`。校验器按档案分别检查，避免为了兼容旧引擎继续污染新内容。
- 叙事优先 NPC 必须声明 `motivation`、`voice` 与定性的 `initial_relationship`。数值 `rapport` 不再属于内容状态。
- 叙事优先 storylet 只允许 `world_beat` / `after_world` 锚点，并且不能再使用 `intent`、`intent_any`、`object_any` 或 `object_all` 作为行动路由条件。

## Phase 2 批次 A：最小后验闭环

### 本批目标

把 Phase 1 留下的 `FactBatch` 提交缝接到真实候选散文：模型只负责抽取无权限事实，代码负责把受支持事实转换成 patch；冲突候选有限重写，最终失败保持回合与状态为零变化。

### 不可信事实抽取

- 协议升级为 0.3，新增 `FactExtraction` 与五类判别联合事实：人物移动、物品转移、秘密披露、新承诺、承诺状态更新。
- 每条事实必须包含候选散文中的逐字 `evidence`。`item_transfer` 同时携带 extractor 看到的 from/to placement，用于乐观归属复验。
- provider 新增 `extract_facts`。DeepSeek 使用独立 JSON prompt 和一次格式修复，混合批次中任何畸形 fact 都会使整次解析进入修复而非被静默丢弃；scripted provider 支持端到端夹具；mock extractor fail-closed 返回空事实，不重新引入手写自然语言路由。
- `FactExtraction` 不能携带 dotted path 或状态 patch；只有检查器能生成可提交的 `FactBatch.state_changes`。

### 铁律检查

- 人物移动要求作者人物、当前可见、已有权威位置，目标是当前可用相邻出口；同批不能移动两次。
- 关键物品转移要求物品可见、portable、from placement 与账本精确一致、目标人物/地点存在且交接双方同场；同批不能转移两次。
- 秘密当前只允许作者人物本人向同场听众披露自己的 `secret`，披露记录写入 `disclosures`，玩家听到的摘要进入已知事实。
- 新承诺要求双方同场、关联物品存在且可见；记录写入 `commitments`。open 承诺可进入 fulfilled / broken / cancelled；关联物品承诺只有同批完成交付才能标记 fulfilled。
- 任一事实失败则不生成 batch。陈旧 extraction 和证据不在原文属于不可重试错误；其余冲突默认允许候选散文重写一次。

### 提交、时间线与感知

- CLI 现在执行“候选散文 → FactExtraction → 铁律检查 → 最多一次重写 → FactBatch 原子提交”，删除 `fact_extraction_deferred` 占位事件。
- trace 新增 `fact_extraction`、`iron_law_validation`、`narrative_regeneration` 与 `turn_committed`。
- 每次成功提交生成协议级 `CommittedTurn`，按 iron_law / canon_anchor / local_canon 标记变化来源，并随 checkpoint 深拷贝保存。
- state 新增 `disclosures` 与 `commitments` 权威命名空间。物品增加可选 `visible_when_carried`；默认隐藏同场人物库存，只有作者明确声明为明显可见的携带物才进入主体感知。
- 收紧提交后 Director 旁路：未经抽取的 `react` / `advance_plan` 摘要只留 trace，不进入玩家输出或 recent memory；合法进场只显示引擎根据已提交人物与地点合成的提示，模型摘要不能夹带承诺或披露。

### 开放夹具验收

新增两回合场景回归：

1. 周师傅明确承诺次日把旧防雨布交给玩家，只提交 open commitment，物品仍由周师傅保管；
2. 后续散文明写交付，extractor 同批提出 item_transfer 与 commitment fulfilled；检查通过后物品进入玩家持有、承诺标记兑现并触发结局。

另覆盖非法密室移动的冲突重写，以及连续两次非法候选后 state / turn / revision / checkpoint 完全不变。

### 诚实边界

- 自由文本 `constraints` / `boundaries` 仍是生成约束；当前代码只检查实体集合、空间图、可见性、物品归属、秘密所有者与承诺状态等结构化边界，通用世界边界 DSL 尚未实现。

## 真实 DeepSeek 试玩复盘：剧情连续性与展示内容

### 试玩路径与可审计结果

使用 `deepseek-v4-flash` 运行《晚风中的一桌饭》，只通过 `ideas` 选择“提议天台野餐”。旁白让陈阿姨口头同意并开始往楼梯间走，但 extractor 返回空 facts；因此玩家与陈阿姨仍停留在 `building_lobby`，`current_goal` 未变化，本回合只有 `opening_offer` 锚点提交。随后 Director 的两次 JSON 请求都返回空 `message.content`，被可选层降级为 `Director unavailable`，玩家回合本身已经成功提交。

对应审计文件：`data/traces/55b9b19769a5.jsonl` 与 `data/sessions/55b9b19769a5.jsonl`。运行日志不加入版本库，只在此记录结论。

### 暴露的问题

1. **DeepSeek 调用没有显式控制 thinking。** DeepSeek V4 当前 thinking 默认启用，推理内容与最终 `content` 分字段返回；AIRPG 只读取 `message.content`，结构化调用也没有记录 `finish_reason`、`reasoning_content` 或失败响应 usage。Director 仅给 700 个输出 token，可能在最终 JSON 前耗尽，也可能命中 DeepSeek 官方说明的 JSON Output 偶发空内容。现有 trace 无法区分两者。
   - Thinking Mode：<https://api-docs.deepseek.com/guides/thinking_mode/>
   - JSON Output：<https://api-docs.deepseek.com/guides/json_mode/>
2. **`ideas` 只有单批文本去重，没有跨回合语义连续性。** 建议器不知道“上一轮已经提议且 NPC 已同意上天台”，也没有已选行动、已回应命题、开放剧情线程或语义签名；权威地点和目标不变时，它会再次提出同一选择。五个固定 focus 保证的是当批表面差异，不是剧情承接。
3. **软叙事没有视角校验。** 旁白写出“她没说自己其实有点喘”，这是玩家不可直接知道的人物内在状态；Phase 2 只检查移动、物品、披露和承诺等硬事实，未阻止这类内容进入 recent memory，下一轮建议又把“气喘”当成已感知前提。
4. **当前 Director 不是剧情导演。** 它在事实提交后运行，只保守调度既有人物进场、反应节拍和 Local Canon；即使 provider 返回成功，也不能为下一回合建立场景方向、开放线程或 NPC 自主决定。此次 API 空响应放大了问题，但不是建议停滞的根因。
5. **《晚风中的一桌饭》仍是任务型样例。** `current_goal`、`dinner_agreed`、`table_set`、`guest_count`、物品准备与条件结局构成了清单式推进；它验证了位置、物品、锚点和结局，却不能代表“剧情自行发展、玩家参与其中”的目标体验。

### 当前判断

- 暂不把问题归因于 `deepseek-v4-flash` 的模型能力，也不优先换模型；先修正调用模式、输入上下文和输出可观测性，再用同一模型复测。
- `ideas` 必须成为可选的剧情承接入口：即使玩家只选建议，也应持续前进。候选可按“顺应当前发展 / 引发冲突 / 推进开放线程 / 引入有根据的意外”等戏剧功能区分，但不能恢复为机械能力菜单。
- 《晚风中的一桌饭》保留为 Phase 2 回归故事，不再作为最终体验标杆。新的主展示故事应从零按剧情优先创作：没有任务清单，场景会自行演进，人物有各自动机，结局描述关系与未竟之事，而非完成度。
