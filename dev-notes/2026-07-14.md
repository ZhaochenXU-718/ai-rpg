## 问题与思考

### 僵硬感的定位：政策级决定，不是缺模块

判断依据是一个反事实：即使按现有政策把 README 里所有缺的模块（对话、战斗、经济、Web UI）补完，僵硬感也不会消失，因为封闭结果空间的是三处**有意写下的政策**：

1. **静态路由白名单**：`capabilities.py` 的 `available_tools` 只从故事声明的 intents × objects 派生工具，表外能力一律 `capability.unavailable`。
2. **fail-forward 只给软代价**：`allow_unauthored` 路径加上 engine-principles §5 的明文规定（"未预写尝试只能消耗时间 + 白名单软代价 + 零 canon 效果，没有破例"）。
3. **Canon 是封闭集合**：`AuthorityLevel` 在 SOFT_STATE 和 CANON 之间没有中间层，LLM 提议的任何持久新事实都被 `change.authority_reserved` 剥离，因此不存在"经过验证的生成式事实"。

值得注意的是 **README 的终局愿景与竞品分析结论本来就一致**（"storylet 不是行为白名单而是因果锚点""创作者是立法者不是枚举程序员""锚点之间由 LLM + 能力模块即兴填充"）。真正落后的是 engine-principles §5 的硬政策和 v0.1 实现。所以这不是推倒重来：协议、revision、原子提交、感知墙、trace 全部保留，要改的是控制边界的划法。这与 07-13 第四批"能力层缺口"的架构判断相互印证——竞品分析从外部独立得出了同一结论。

### 《秘法学院》实例考察：头部故事的创作面到底有多小

实地翻了 ISEKAI ZERO 头部作品《秘法学院》（648k 消息、2k 场聊天）的公开发布页，关键事实：

- **全部作者内容约 14k tokens**（故事线 ~7k + 11 张角色卡 ~7k），三个开场各 430–560 tokens，约 20 页文本。没有场景图、没有行动枚举、没有任何"意图 × 对象 × 结果"组合。这是"组合爆炸不可持续"论断的直接实证。
- 创作面拆解为六类：①世界法则与系统（假面法则、七大书库魔法系统、共鸣度 0–100% 决定成功率、血脉等级、派系格局、排名与决斗规则——全是"立法"，没有一条是剧情分支）；②11 张人物卡（身份、动机、关系倾向）；③3 个开场初始状态快照；④**秘密钩子**：用乱码字体公开承诺"存在秘密"（第八书库、创始人办公室、学生失踪事件），甚至公开达成条件轮廓（"需要七个书库完美和谐运作"），但不泄露谜底；⑤**世界行为契约**（"没有主角光环、NPC 独立行动、失败有持久后果、软弱的论点无法说服他人"）——本质是一份判定政策宣言；⑥"剧情"标签对公开访客显示"暂无描述"，主线不公开。
- **对 AIRPG 最重要的洞察**：那份行为契约的每一条承诺，ISEKAI ZERO 只能靠 prompt 恳求模型遵守，数值与后果一致性是软的；而这些恰恰是 AIRPG 的账本、能力模块和原子提交在结构上就能保证的东西。正确姿势：**创作面向他们看齐（小而立法式），兑现机制用自己的（结构性）**。这就是差异化本身。

### LLM 行动提案比机械意图菜单更接近最终交互

ISEKAI ZERO 在自由输入之外提供一组由 LLM 生成的提案卡，每张卡包含标题和第一人称行动 / 对话描述，并从汇报、调查、幽默、人物互动或局势变化等不同侧重点继续当前场景。相比 AIRPG 当前的"选择意图 → 猜测目标 → 补充描述"，这种设计显著降低空白输入负担，也能用当前上下文维持叙事连续性。当前 intent 菜单和对象 ID 是开发脚手架，最终产品不应把底层能力词汇直接暴露给玩家。

需要修正一个最初误判：截图中的"新角色加入"并非凭空生成新的重要人物。复核[《秘法学院》公开页](https://www.isekaizero.ai/storylines/69e0e01718959326aabeaa73?snapshotType=chat-storyline)后，页面列出了 11 张关联角色卡，截图中出现的埃琳娜、卡修斯等均属于作者预定义人物。公开信息不能证明平台永远不生成无名路人，但足以支持更稳妥的判断：**重要人物由作者预定义，LLM 负责让既有人物在合适时机进入当前场景并参与剧情**。所谓"新角色"更可能是"对当前场景新出现的角色"，不是"对世界新创建的实体"。

截图中的提案因此仍有两种控制权，但区别是"谁采取行动"而不是"是否创建人物"：

- **玩家行动提案**：玩家准备说什么、做什么，应落为可验证的 `ActionPlan`；
- **下一幕 / 导演节拍提案**：既有人物进场、某人表现担忧、允许的局势发生变化，应落为受动机、位置、日程和世界规则约束的 Director Beat。

这揭示出一个低创作成本且连续性更强的模式：作者写重要人物卡和世界法则，LLM 动态编排"谁在何时何地介入"，而不是让作者预写每次出场，也不是让模型随时创造新的核心人物。

### 倒计时、报价与 LLM 不确定性的耦合

当前两个样板故事都把 `world.time_left` 当作每回合消耗的资源，这源自《午夜前的档案室》的题材需要，却在实现和文档中逐渐变成了默认游玩契约。这个默认不适合以自由尝试为中心的 LLM 叙事：玩家不仅不知道行动结果，还要承担模型可能理解错误的成本，于是每次输入都同时包含"世界风险"和"模型风险"。为了避免误伤而增加的完整报价又把理解、规则和确认步骤持续摆在玩家面前，进一步破坏沉浸。

需要拆开三个概念：

- `turn_no` 是分支内排序、回放和世界步进的逻辑序号，不是玩家资源；跨分支全局顺序由单调 `state_revision` 与日志时间确定；
- 世界时间用于昼夜、日程、旅行和 NPC 行动，仍是通用模拟能力；
- 每行动一次就逼近失败的倒计时是特定题材的压力机制，只应由故事选择启用。

ISEKAI ZERO 的撤回、重做和消息分支提供了另一种处理 LLM 不确定性的方式：先让玩家尝试，不满意再返回上一个节点。AIRPG 不能只删除一条聊天消息，因为每条消息背后可能已经提交位置、物品、关系、storylet 消耗、世界事件和后续 Local Canon；需要的是与消息树对应的**权威状态树**。撤回应从旧提交点创建新分支而不是抹除历史，旧 trace 保留，当前分支的状态、叙事记忆和模型上下文一并切换。

还要区分三种容易混淆的操作：

1. **重新生成叙事**：只重写散文，复用同一个 `CommittedOutcome`，权威状态不变；
2. **撤回并修改行动**：恢复父提交的完整快照，从该点创建新状态分支；
3. **重新检定**：是否允许用新随机结果重做行动属于玩法政策，不能伪装成重新生成文字。

## 形成的结论

### 作者主权边界（已写入正式契约）

| 归属 | 内容 | 对应机制 |
|---|---|---|
| **作者必须定** | 世界法则与物理常数；判定系统选装与参数；核心人物的身份、动机、关系与秘密；秘密的谜底与披露条件；少量剧情锚点与结局条件；开场初始状态；尺度、风格与禁区 | 核心 Canon + resolution_limits + perception + 能力模块配置 + storylet（降级为锚点后的职责） |
| **作者可选定** | 地点 / NPC / 物品的原型清单与生成预算；派系成员密度；支线钩子 | 新增：生成约束声明（LOCAL_CANON 的立法依据） |
| **引擎裁决** | 行动可行性、成本、检定、资源与位置账本、秘密披露时机 | 能力模块 + resolver + 感知墙 |
| **LLM 生成** | 对话、场景细节、路人、次要 NPC 反应、锚点之间的过渡、玩家解法的具体展开 | 表现层自由 + 通过验证后晋升为 LOCAL_CANON |

对照 content-schema，"作者必须定"一栏现有字段基本覆盖；**多出来的负担恰好是 intents 枚举和 storylet 的白名单职责**——它们不在任何"必须"里，这就是要开放的部分。需要新增的立法工具只有一个：原型与生成预算声明。

核心 / 重要 NPC 应进一步明确为 Core Canon：身份、动机、关系和秘密由作者提供，LLM Director 只负责调度其进场、反应和计划。无名路人可以停留在表现层；只有玩家持续互动、确实需要被世界记住的次要人物，才考虑经过约束晋升为 Local Canon。Local Canon 第一版不必承担动态创建重要 NPC 的职责，NPC 晋升甚至可以在地点和局部局势之后再做。

### 时间压力、撤回和报价的重新定位

决定不是彻底删除时间，而是删除"所有有效行动默认扣倒计时"这一通用假设：

| 游玩配置 | 时间机制 | 撤回 / 分支 | 事前报价 |
|---|---|---|---|
| **自由叙事（默认）** | 无倒计时；世界时间按需要存在 | 开启 | 仅真正不可逆行为 |
| **世界模拟** | 日程或事件驱动，只有确实耗时的能力推进时间 | 开启 | 高风险不可逆行为 |
| **悬疑挑战** | 作者可选显式倒计时 | 可限制 | 高风险、稀缺资源与不可逆节点 |
| **硬核模式** | 强时间压力 | 可关闭 | 完整公平报价 |

默认交互从"复述—报价—确认—提交"改为：

```text
玩家输入
→ LLM 理解
→ 能力模块验证和裁决
→ 自动提交可逆结果
→ 展示叙事 + 机械回执
→ 继续 / 撤回修改 / 创建分支
```

澄清、理解失败、重规划、查看状态、重新生成叙事、放弃方案和切换分支永远不推进世界时间。即使故事启用了倒计时，也应由能力模块判断旅行、搜索、制作、战斗或等待等行为是否真的耗时，而不是给所有对话和观察统一附加 `time_left: -1`。

报价不再承担"所有行动的安全网"职责。低风险和可逆行动直接执行，检定在结果后展示机械回执；只有死亡、永久伤残、关键关系永久破裂、唯一物品消耗和不可逆主线转折等行为需要完整事前确认。作者可以配置阈值或开启硬核配置，但具体风险等级优先由能力模块根据真实效果推导，避免作者重新枚举每个 intent。

撤回 / 分支属于运行时核心而不是故事模块。每个提交节点至少要关联父提交、权威状态、storylet 消耗、临时效果、近期事件、叙事记忆和随机源状态。恢复旧节点后必须产生新的单调递增 revision，所有旧报价与验证结果立即失效，不能因为回到相似状态而复用陈旧计划。完整消息树 UI 可以后置，但最小 checkpoint / branch 语义应在 Local Canon 之前确立，否则动态生成实体还要重新补回滚协议。

### 行动提案层与 Director Beat

最终交互应同时保留自由输入和 3—5 张动态提案卡，但提案不是未经验证的续写文案，而是能力系统之上的自然语言展示层：

```text
PlayerPerception + 当前目标 + 近期事件 + 可用能力工具
→ LLM 生成多个候选提案
→ 每个候选转成结构化 ActionPlan / Director Beat
→ 引擎按当前 state revision 验证、去除越权项
→ 按目标、能力、对象和侧重点去重
→ 展示 3—5 张提案卡
```

玩家选择一张行动卡时应执行它已经验证过的 plan，不再把卡片文字送回 LLM 重新理解；玩家编辑文字后才重新规划。状态 revision 改变后，旧卡全部失效。卡片只能描述"准备尝试什么"，不得保证尚未裁决的结果或泄露感知墙后的秘密；自由输入框始终保留，并明确提案只是灵感而非行为白名单。

Director Beat 使用作者预定义角色池和世界事件池。例如"卡修斯加入当前餐桌"应引用既有 `character_id`，再验证他的当前位置、可达路径、动机和日程；这属于既有实体调度，不需要 Local Canon。只有提案要求产生状态中不存在的持久局部事实时，才进入 Local Canon 提议与预算检查。

### 调整后的落地顺序

1. **第 0 步：守则修订与可测基线（先行）**。废除 / 替换 engine-principles §5 的 fail-forward 硬政策，起草 `docs/authoring-contract.md`，把"默认无倒计时、可逆行动自动执行、事后回执、状态分支"写入 README 目标契约并按修订约定留痕。开放性指标前置：trace 增加结果来源、主目标是否达成和是否只有代价，避免把"关系 +1 但没借到桌垫"误计为有效行动。
2. **第 1 步：默认交互契约修正 + 最小状态时间线**。让自由文本路径真正遵守低风险免确认；移除通用的每回合扣时假设；先实现内存级 checkpoint、撤回、分支和 revision 失效语义，不急着做完整消息树 UI。
3. **第 2 步：阶段 A 开放场景 + 第一个通用能力纵切（核心工程）**。先写"只有世界、动机、边界和一个终局锚点、刻意不写解法 storylet"的测试夹具；首个纵切选 `social.request_item`，让"向罗叔借桌垫"能够得到物品转移、条件交换或明确拒绝，而不是只提交 rapport。通用裁决引入的不确定性档位通过事后机械回执展示，只有不可逆结果才进入报价。
4. **第 3 步：LLM 行动提案层 + 既有人物调度**。建立 `SuggestedAction` / `DirectorBeat` 协议；提案必须引用当前可用能力或作者预定义角色 / 事件，经过感知墙和 revision 验证后才展示。先替换机械 intent 菜单，再逐步接入 NPC 动机规划。
5. **第 4 步：LOCAL_CANON + 实体晋升（最小版本）**。建立在能力结果、状态分支和 Director Beat 语义之上；第一版优先支持局部地点和局势，硬性限制生成预算和 local 生命周期。核心人物禁止临场创建，次要 NPC 晋升根据试玩需求后置。

明确后置：Chapter / Arc 长期摘要、完整消息树 UI、全部产品外壳。两个样板故事停止增加补洞型 action / storylet，转为回归夹具；《午夜前的档案室》保留为可选倒计时模式样本，《晚风中的一桌饭》应改为无倒计时或软日程样本。

一次只做一个通用模块：第一个模块的真正产出不是模块本身，而是"生成式提议 + 确定性裁决"的协作接口；接口定对了，后面的模块都是填空。

### 假设（尚未验证）

- **可公开的秘密轮廓**：借鉴《秘法学院》乱码钩子的做法，让作者在 perception 里声明"玩家可知道秘密存在及触发条件轮廓，但不可知道谜底"。感知墙目前只管"藏"，这个扩展回答"玩家为什么要探索"。schema 改动小，价值待试玩验证。
- **分支对悬疑挑战的影响**：自由叙事默认允许回看不同选择会提高玩家的元知识；这在默认模式中视为玩家自主权，在悬疑挑战 / 硬核配置中是否允许限制撤回、重新检定或秘密节点回退，待真实试玩验证。
- **提案多样性与玩家自主权**：动态卡片可能降低输入负担，也可能把玩家注意力收窄到模型给出的路径。需要用提案采用率、编辑率、提案后撤回率、候选验证淘汰率和能力 / 目标多样性衡量；UI 必须持续强调自由输入与提案等价。
- 风险分级的交互档位暂定为自动执行 / 检定后回执 / 完整事前确认 / 硬边界拒绝。阈值优先由能力模块依据真实效果推导，作者只配置世界尺度、模式和少量覆盖；具体协议待第 1、2 步联合设计。

## 同日第四轮：最小 Local Canon（第四步实现）

按调整后落地顺序的第 4 步实现生成式局部事实，建立在既有的状态分支与 Director Beat 语义之上。范围严格收敛：只支持局部地点与局势两类原型、原型清单由作者声明、硬性生成预算、local 生命周期；禁止生成任何角色。

### 设计决定

- **提议通道唯一**：Local Canon 只能由 Director 通道提议（`DirectorResponse.local_canon`，每回合硬上限 1 条）。`ActionPlan.proposed_changes` 中的 `local_canon` 权限提议沿用既有 `change.authority_reserved` 剥离——行动理解层永远不能创造实体，防止玩家指挥模型绕过准入。
- **`gen_` 命名空间是协议级强制**：`LocalCanonProposal` 的 model validator 直接拒绝无前缀 ID，生成实体在任何 trace 和状态转储中的 provenance 结构性可见，且不可能遮蔽作者 ID。
- **预算按分支累计创建数计算，过期不释放**：软回收会让高频churn制造无限实体；硬总量才是作者实际配置的承诺。
- **生成实体不得嵌套**（父地点必须是作者地点）：v1 的深度限制，防止生成世界脱离作者锚点自我繁殖。
- **回滚零新协议**：生成实体写入 `state.generated` 命名空间，随 checkpoint 快照自然参与撤回与分支——这正是把状态时间线排在 Local Canon 之前的回报，一行回滚代码都不需要。
- **角色不可生成是类型级约束**：`LocalCanonKind` 枚举只有 `location` 和 `situation` 两个成员，没有字段可以携带人物。

### 实现情况

- 协议层：`AuthorityLevel.LOCAL_CANON`（介于 mechanical 与 canon 之间的"经验证生成事实"层）；`LocalCanonProposal` / `LocalCanonValidation` / `CommittedLocalCanon`；`CommittedOutcome.local_canon`。
- 内容 schema：顶层可选 `generation` 块（`budgets` + `location_archetypes` / `situation_archetypes`，含 `allowed_parents` / `allowed_locations` / `max_duration_turns` / `expiry_narrative`），缺省禁止一切生成；校验器新增 `validate_generation`（预算键与取值、原型 ID 形态与重名、父地点存在性、生命周期正整数、预算与原型不匹配警告）。
- 引擎：新增 `server/engine/local_canon.py`——`generation_context` 组装 provider 可见的生成边界；`validate_local_canon` 做原型 / 预算 / ID 冲突 / 名称与 Canon 冲突 / 父地点 / 生命周期 / revision 准入；`commit_local_canon` 原子写入并产出 `local_canon.<entity_id>` 来源的 `CommittedChange`；`expire_situations` 按回合钟点滚动过期。
- 运行时接入：生成地点自动获得"父地点 ↔ 生成地点"双向出口（`available_exits` 派生，移动 / 感知 / 报价全部复用既有 move 语义）；活跃局势进入感知实体与可交互对象；`generated.*` 路径归类 `local_canon` 权限；局势过期在 resolver 第 5 步与临时效果同钟点处理，归因 `local_canon.expiry` 并展示原型 `expiry_narrative`；回执新增"新增局部事实：〈名称〉〔地点 / 局势〕"专行，原始记录不再以字典形式刷屏。
- Director 接线：`run_director_cycle` 组装 generation 上下文（含剩余预算与既有生成实体），逐条准入 provider 提议，拒绝项带 issue 码进入 `director_trace.rejected`；接受项与玩家行动共享同一份 `CommittedOutcome` / checkpoint，一次撤回同时消失。
- Provider：DeepSeek director prompt 升级 v2（输出 `{"beats": [...], "local_canon": [...]}`，无生成边界时强制空数组；坏 ID 清洗补前缀而不修复成权威）；ScriptedProvider 支持 `local_canon_batches` 供确定性测试；mock 保持保守不提议。
- 夹具与测试：开放场景夹具声明 1 地点 + 1 局势的最小生成边界；新增 `tests/test_local_canon.py` 19 项，覆盖协议约束（前缀、地点禁过期）、全部准入拒绝码、预算耗尽、嵌套拒绝、提交后可达与感知、局势按期过期、每回合限流、拒绝零状态残留、撤回后实体消失、DeepSeek 解析（含无生成边界时忽略）。
- 文档：content-schema 新增第 18 节；action-suggestions-and-director-beats 新增第 7 节（Local Canon 提议协议）；llm-action-plan-protocol 权限表补 `local_canon` 行；README 现状对照 / 演进顺序（第 5 项完成）/ 修订表 v0.5。

### 验证结果

- 129 项单元测试全部通过（110 存量 + 19 新增；仅更新一处 director prompt 版本断言 v1 → v2）。
- 两个故事与开放场景夹具内容校验 0 warning；7 条 walkthrough 全部通过。
- 撤回回归确认：提交生成地点 → 移动进入 → 两次 undo 后 `generated` 命名空间与派生出口均不存在。
