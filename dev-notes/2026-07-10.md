# 2026-07-10 开发记录

## 今日主题

复盘《午夜前的档案室》的多轮试玩和修复过程，重新确认 AIRPG 的产品方向：它不是只服务于悬疑解谜的规则引擎，而应成为一个以 LLM 为认知与创作核心、以确定性世界状态为基础的通用 RPG 框架。

## 问题与思考

### 一个短篇故事的创作成本已经过高

《午夜前的档案室》到目前只有一次真人成功通关，但此前已经反复修改了人物位置、场景返回、背包、物品使用、可见性、交互目标、时间预算和错误反馈。主要问题包括：

- 场景对象最初混淆了“存在、可见、可用、已持有”几种含义。
- 人物缺少权威位置，可能在多个场景中同时出现。
- 玩家取得钥匙后缺少背包、使用和返回动作。
- 线索文字指向“暗格”，实际触发器却要求“文件柜”。
- 未发现的暗格提前显示，任意观察又可能错误地发现暗格。
- 无效的使用和潜入会静默失败、扣除时间或错误增加回合数。
- 报价显示的变化和 storylet 最终效果可能不一致。

这些问题说明，当前故事 YAML 包含太多相互依赖的低层事实。主故事已经接近一千行，更像引擎运行时的编译产物，不适合作为创作者长期手写和维护的主要格式。

### 引擎存在变重和过拟合风险

世界棋盘、物品唯一位置、状态事务和条件效果等机制具有通用价值；但当前报价和显示层已经出现 `trust`、`suspicion`、`fire_risk`、`time_left` 等悬疑故事特化。如果每次试玩都通过增加一个核心字段来修复，引擎最终会被《午夜前的档案室》定义，而不是成为通用 RPG 内核。

与 Open-Theatre 对比后可以看到，两者优化的目标不同：

- Open-Theatre 用较轻的场景、人物动机和情节链驱动 LLM 导演与角色，创作格式轻、对话表现空间大，但不负责严格证明物品、位置、资源和胜负路线的一致性。
- AIRPG 显式维护世界事实，能够验证公平性和可解性，但当前把过多负担直接交给了创作者。

不能简单地用 Open-Theatre 替换 AIRPG，也不能让 AIRPG 继续发展成由规则枚举所有合法互动的传统引擎。

### LLM 不能被边缘化为语言润色器

框架的目标是展现 LLM 在 RPG 中的理解、规划、创造和角色扮演能力。LLM 应负责：

- 理解玩家自由表达的真实意图。
- 将模糊方案拆成可验证的行动计划。
- 组合机制能力，创造作者没有预写的新解法。
- 根据角色动机规划 NPC 行为和长期反应。
- 动态调整剧情节拍、机会和任务路线。
- 在引擎拒绝部分效果后重新规划。
- 承担导演、角色表演、记忆和反思。

确定性内核负责的是世界事实、权限、不变量和原子提交，而不是替 LLM 决定全部玩法。

## 形成的结论

### 采用 LLM 原生、事实受约束的运行循环

目标循环应为：

```text
玩家自由输入
→ LLM 理解并生成 ActionPlan
→ 能力工具验证位置、物品、资源和权限
→ 将拒绝项返回 LLM，允许有限重规划
→ 显示风险报价并由玩家确认
→ 引擎原子提交真实状态
→ LLM 导演安排世界与 NPC 反应
→ 角色记忆和长期计划更新
```

Storylet 应作为剧情锚点、特殊演出和关键因果，而不是所有允许行动的白名单。现有 `requires_storylet_match` 适合无 LLM 的阶段 2 严格模式，但不应成为正式 LLM 创造性行动的默认限制。

### 保留按机制能力组合模块的方向

通用 RPG 不应按“悬疑、恋爱、战斗”分裂成多套引擎，而应按机制加载能力：空间、背包、事实、关系、时间、战斗、经济等。类型只是一组默认能力、UI 和 Prompt 配置。

能力模块不仅提供规则，也要向 LLM 暴露工具、观察信息、可提议效果和不变量。LLM 是大脑，能力模块是工具和世界规则，Core 是事实账本与事务系统。

这个方向仍然成立，但暂时不进行全面插件化重构。第一版只在 ActionPlan 中保留 `capability + action` 接口，并用一个静态 CapabilityRouter 接到当前代码。等获得真实 LLM 行动 trace 后，再依据实际调用方式确定正式模块边界。

### 尽早接入 LLM，但先做单导演纵向链路

现在应停止继续猜测 LLM 将来需要什么，尽快让 LLM 参与行动理解、创造性规划和剧情导演。第一阶段先使用一个导演 LLM，不同时引入多 Agent、RAG、长期记忆和完整前端，以免无法定位问题来源。

现有规则模式、测试和 walkthrough 继续保留，作为离线回归、LLM 故障降级和公平性对照基线。

## 实现情况

今天已经完成并验证的基础能力包括：

- schema v2 世界棋盘和角色唯一位置，NPC 按 world step 移动。
- 物品唯一位置、玩家口袋、显式使用和场景返回。
- 对象 `visible_when` / `actionable_when` 条件。
- 无效动作在报价和扣时前拒绝，不推进 world step、不增加回合数。
- 确定性报价预演、错误展示和会话日志。
- 修复文件柜/暗格目标不一致、暗格提前显示、观察条件过宽和艾拉信任抵消等故事问题。
- CLI 支持中文意图、对象显示名和常见中文分隔符。
- 24 项单元测试、4 条 walkthrough、内容校验和真实 CLI 无徽章路线全部通过。
- 定义 LLM 行动协议 `0.1`：PlayerPerception、ActionPlan、ValidationResult、CommittedOutcome、状态权限层级和 provider-neutral JSON Schema。协议模型只负责校验与序列化，尚未接入真实 LLM 或改变 resolver 行为。

这些能力构成当前确定性基线，后续 LLM 接入不能破坏其位置、所有权、报价和事务不变量。

## 下一步

1. **建立 LLM 接入骨架。** 实现 PlayerPerception 构建器、LLMClient、Mock/Replay 和静态 CapabilityRouter，让协议开始连接当前世界状态和能力工具，但不先引入多 Agent。
2. **打通单导演 LLM 纵向链路。** 先让自由方案完成“理解—验证—一次重规划—报价—提交—导演反应”的闭环，现有规则模式继续作为降级路径。
3. **用真实创造性行动决定后续架构。** 测试一批作者未预写的合理方案，记录完整 trace，确认 LLM 能创造路线且不破坏硬状态；再根据真实数据拆正式能力模块，并用第二个非悬疑 RPG 验证复用性。

近期暂不展开多 Agent、RAG、Web UI、运行时热加载、完整插件系统和更多故事内容。
