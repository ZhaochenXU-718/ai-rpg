# 2026-07-12 开发记录

## 今日主题

落地 LLM 接入骨架的前两块：感知构建器（PlayerPerception builder）与静态能力路由器（CapabilityRouter），并借此完成两项去悬疑化清理。目标对应 2026-07-10 记录的下一步第 1 项。

## 完成内容

### 感知墙（server/engine/perception.py）

- `build_player_perception`：从权威状态构建协议 `PlayerPerception`——位置、可见实体（过 `visible_when`）、口袋、已知线索、可用意图、能力工具、公开状态。这是未来理解 LLM 的唯一输入，也是所有玩家可见界面的唯一披露依据。
- `filter_changes_for_player`：报价披露过滤器。修复报价预言机问题——此前报价卡在执行前直接打印 `flags.hidden_compartment_found`、证据入包、全员移动到终幕、甚至"预计将进入结局：truth_exposed"。现在全量预演仅用于约束力校验和日志，报价卡只披露玩家已可感知的公开状态变化（读**行动前**状态，防止"即将发现的东西"泄漏）。
- 哪些状态算公开由故事 `perception` 块声明（world_state / scene_state / character_state + 展示标签），引擎不含故事词汇。`character_state` 只对与玩家同节点的角色生效。

### 静态能力路由器（server/engine/capabilities.py）

- `available_tools`：由内容意图派生 `intent.*` 工具（含参数 schema 与授权层级），进入 `PlayerPerception.capability_tools`。
- `validate_plan`：ActionPlan → ValidationResult + 执行载荷。v0.1 承兑范围：恰好一个 intent 步骤（一计划=一回合=一份代价）；SOFT_STATE 提议过 `resolution_limits` 裁剪；PRESENTATION 不进状态；MECHANICAL/CANON 剥离（机械由引擎推导、canon 只归作者事件卡）；`perception_revision` 过期报 `plan.stale_perception`。全部拒绝均不扣时、不计回合。
- `build_committed_outcome`：TurnResult → CommittedOutcome，提交路径按 `positions/item_locations → mechanical、白名单 → soft_state、其余 → canon` 推导权限。
- 承兑范围表写入 `docs/llm-action-plan-protocol.md` 10.1，写 prompt 以此为准。

### Session 扩展

- `state_revision`（提交回合数）、近期事件窗口（最近 5 条叙事）、`perception()`、`validate_plan()`、`resolve_plan()`。计划路径复用现有报价绑定语义：执行载荷即验证时裁剪的 patch。

### 去悬疑化（守则 #4 清理）

- `NPC_PROPOSALS`/`SCENE_PROPOSALS`/`hazard_notes` 硬编码删除，改为内容声明：`intents.<id>.fallback_proposal`、`quote_warnings`（条件语法与 trigger 一致）。
- 状态栏 疑/警/信 标签与"剩余时间"改读 `perception` 块；`INTENT_FALLBACK` 文案改为 `intents.<id>.fallback_narrative`。
- 引擎代码中不再出现 trust / suspicion / fire_risk / 悬疑文案；`quote_warnings` 成为确定性引擎下"风险感"的合法来源（描述局势紧张度，而非预告后果）。

### 校验器与测试

- validator 新增 `perception` / `quote_warnings` / `fallback_proposal` / `fallback_narrative` 校验；schema v2 缺 `perception` 块给警告。
- 新增 `tests/test_perception_and_router.py` 9 项：感知隐藏未发现物与不在场角色、口袋与出口、报价卡无预言机回归、计划提交与权限分类、canon 提议剥离、误标 soft 的受保护路径被裁剪、多步计划拒绝、过期修订拒绝、澄清计划不可执行。

## 同日第二批：LLM 纵向链路（Mock）

完成了原"下一步"第 1、2 项：

### Provider 抽象与 trace（server/engine/llm.py、trace.py）

- `LLMProvider` 抽象 + 三个实现：`ScriptedProvider`（测试/演示用预置计划）、`HeuristicMockProvider`（通用标签匹配，只认识感知暴露的实体与意图标签，不含故事词汇——它无法引用玩家看不见的东西，天然遵守感知墙）、`ReplayProvider`（从 trace 回放解析后的计划）。真实 provider 实现 `propose_plan` 注册进 `PROVIDERS` 即可，下游全部 provider 无关。
- `TraceRecorder`：按协议 §11 落盘 JSONL（data/traces/，已 gitignore）：perception、原始响应、解析计划、validation、重规划、确认的报价、CommittedOutcome、模型/latency/usage。

### 纵向闭环（server/engine/llm_loop.py + CLI）

```text
custom 自由文本 → 感知 → propose_plan → validate_plan
  →（错误且可重试：带上一轮验证结果重规划一次）
  → 报价（理解文本来自计划，提议即验证载荷，披露过感知墙）
  → 玩家确认 → resolve_plan → CommittedOutcome → 渲染
```

- 公平性约定全程保持：澄清/被拒计划不扣时、不计回合；报价的提议与提交的载荷是同一份；理解失败显式告知而不猜测执行。
- CLI `--llm mock|off`（默认 mock）：`custom` 意图输入自由文本即走链路；`off` 退回结构化对象输入。计划路径一律出报价卡确认理解——即使意图本身低风险，因为理解可能出错。
- 实测：「我借着雨声观察一下侧梯和全家画像」→ observe + [rain_noise, side_stair, family_portrait] → 一回合触发画像、便签、侧梯三张卡。

### 已知留白（等真实 LLM）

- Mock 不做越界分类（`out_of_bounds`）：违反世界边界的方案会被降级为 custom 而不是世界内拒绝——输入分类本来就是真实理解层的职责，mock 不模拟。
- 重规划策略是"降级为 custom"，真实 LLM 应基于 ValidationResult 的 issues 真正修正方案。

### 验证

- pytest：45 项通过（新增 6 项：有效计划全 trace 提交、拒绝后重规划零成本、双拒终止、澄清零成本、启发式感知接地、trace 回放复现）。
- 内容校验 0 警告、4 条 walkthrough 通过、CLI 实测链路与 trace 落盘正常。

## 同日第四批：渲染层、澄清延续与 fail-forward（首次真实试玩反馈驱动）

DeepSeek 真人试玩暴露三个问题，按讨论确认的顺序实施：

### LLM 叙事渲染（server/engine/narration.py）

- `NarrativeRequest/Response` + `LLMProvider.render_narrative`（默认 None → 模板回退）；DeepSeek 实现纯文本模式（非 JSON），温度 0.7。
- 事实清单在感知墙内组装（`build_turn_facts`）：作者叙事提示为骨架、可见状态变化过 `filter_changes_for_player`、公开状态快照按 `perception` 配置；测试断言清单里不含证据/结局/positions。
- 渲染 prompt 硬约束：只能陈述事实清单、不得虚构成功；"本回合无预设事件"显式标注，让失败的尝试被如实叙述。
- 拒绝也走渲染（`narrate_rejection`）：世界内口吻解释为什么行不通，原始原因仍打印作为公平回执。
- 渲染失败/为空静默回退模板，叙事永不阻塞回合；trace 记录 narration 事件（模型/延迟/usage/文本）。

### 澄清上下文延续

- session 持有 `pending_clarification`（澄清计划 + 问题）；下一次自由输入作为回答注入 PlanRequest（`待澄清问题` + `上一轮计划`），模型不再靠"口袋里只有一把钥匙"的运气理解"是的用它"。
- 复用协议的 revision/parent 链（任何带 previous_plan 的提案自动 revision+1）；非澄清回合消费未决澄清，提交后清除。

### fail-forward 判定政策（allow_unauthored）

- LLM 计划中"目标合法 + 做法完整 + 作者未预写"的尝试不再免费拒绝：报价明示"没有把握"（ADJUSTMENT issue `action.unauthored_attempt`），执行消耗时间、软代价照白名单裁剪、canon 零效果、判定 fail_forward。
- 修复公平性漏洞：免费拒绝可零成本探测作者预写面（上局玩家在 time 0 免费试了三次）。
- 结构化无 LLM 路径保持阶段 2 严格模式（回归测试锁定）。

### 验证

- 63 项测试通过（新增 9 项：事实清单感知安全、无事件回合诚实标注、DeepSeek 纯文本渲染、空渲染回退、拒绝的世界内叙述、澄清跨输入延续 ×2、未预写尝试扣时提交、结构化路径仍严格）。
- 内容校验 0 警告、4 条 walkthrough 通过、CLI mock 路径模板回退正常。

## 同日第五批：真实 DeepSeek 试玩复盘——裸 custom 触发的语义碰撞

第二次真实试玩整体质量显著提升（澄清能列出在场人物、叙事渲染融合作者提示、玩家 7 回合达成代价胜利），但暴露一个必然爆炸的内容层炸弹：

- **现象**：玩家输入"和薇拉小姐交流，打听遗嘱的事情"，确认报价后被直接送进仆役走廊。
- **根因**：`slip_into_corridor` 等三张转场卡的触发是裸 `intent_any: [sneak, custom]`，无对象约束。阶段 2 里 custom 是罕见的兜底输入；接入 LLM 后 custom 承载**一切**自由文本行动，任何不贴近具体意图的方案都会撞上转场卡。
- **叠加因素**：感知墙把 `positions.*` 全部挡在报价披露之外，玩家自身的移动也没显示——确认了才发现自己走了，报价约束力形同虚设。

修复（按守则分层）：

1. **内容**：三张转场卡（slip_into_corridor / climb_back_stairs / archive_entry_by_distraction）补 `object_any` 路线对象约束——转场必须指涉路线本身。
2. **校验规则**：custom 触发 + 重效果（move_entities/move_items/set_world）+ 无对象约束 → 警告；下一个故事写不出同样的炸弹。
3. **报价协议**：感知墙开一个明确定义的例外——玩家**自身**移动是自己行动的一等后果，报价卡新增"预计移动：A → B"；其他实体位置与隐藏事实照旧不披露。
4. **Prompt**：意图选择规则加强——"交谈/说服/打听"应选交涉，custom 是最后手段（这局模型把"和薇拉交流"映射成了 custom 而不是 negotiate，是碰撞的另一半原因）。

验证：66 项测试（新增 3 项：无关 custom 行动不再转场、指涉路线的 custom 仍可转场且报价显示移动、校验器抓裸 custom 重效果卡）、内容校验 0 警告、4 条 walkthrough 通过。

## 同日第六批：去词汇化——通用引擎审计发现的三处泄漏

复盘"计划是否过度聚焦悬疑类型"时在引擎代码里审计出三处类型词汇泄漏（守则 #4 违例）。架构结论：**验证方法论整个建立在单一样本上**——问题二"换一个故事还会发生吗"至今只靠思想实验回答，从未被经验检验。

三处泄漏与修复：

1. **`clues` 是引擎一等公民**（state 初始化、resolver 追踪、renderer"已获线索/新线索"文案、CLI `clues` 命令）。"线索"是悬疑词汇；机制本身（append-only 玩家知识日志）是通用的。→ 引擎概念改名 `facts`（effect 关键字 `add_facts`、`TurnResult.new_facts`、报价内部 `expected_fact_count`），展示称呼由故事声明 `perception.facts_label`（本故事"线索"，缺省"发现"；情感剧可以叫"回忆"）。校验器对旧关键字 `add_clues` 给出改名迁移报错；CLI 命令改为 `facts`（保留 `clues` 别名）。
2. **DeepSeek prompt 规则 3 硬编码「交涉」意图名**（上一批修 custom 碰撞时引入）。→ 规则改为"每个意图的适用范围以 capability_tools 描述为准"；社交词汇搬进内容层 negotiate 的 description（"与人交谈、打听消息、说服……"）。试玩教训保留，位置搬到了它该在的层。
3. **renderer 硬编码 `world.time_left`** 判断"是否只有时钟在走"。→ 改判意图声明的 `typical_cost` 路径（复用 resolver 的 `world.` 前缀语义）；CLI 结局收尾行同步改为按 `perception.world_state` 配置输出。

验证：66 项测试、内容校验 0 警告、4 条 walkthrough、CLI 冒烟（facts 命令 + 线索标签）全部通过。

## 同日第七批：真实 DeepSeek 试玩 #3 复盘——六问逐一查证（trace: 81c169035f6f）

去词汇化落地后玩家打了第三局真实 DeepSeek（结局：证据被毁，9 回合）。六个体验问题全部用 trace、内容触发条件和 CLI 代码查证到根因。总判断：**判定核心零误判**（信任门槛、canon 保护、无效输入不扣时、时间记账全部正确），所有问题都在它外面的可迭代层。逐条：

1. **终端丢字（新问题类，A 类脚手架）**："和薇拉小姐交流遗嘱的事情"到达 LLM 时是 `'和交流遗嘱的事情'`——名字在 `input()` 之前的终端/输入法层丢失，整局多次发生（潜入→潜、钥匙环→钥环、欺骗→欺）。已核证引擎与 CLI 字符串处理无损（`extract_free_text` 逐字、`player_text` 取自请求侧、readline 未加载）。**trace 记录 player_text 的审计价值获证**——没有它这类问题会被永远归咎于模型。
2. **CLI 路由缺口（C 类接线）**：澄清后的裸文本回答（"和薇拉小姐交流"）撞上"每行必须以意图开头"报未知意图——session 层的澄清延续做了，CLI 分发器没接线。对 LLM 原生引擎，"裸自然语言进不了理解层"本身是阶段 2 遗物。
3. **节拍卡与玩家行动混叙（C 协议 + B 校验盲区）**：`negotiate(heir)` 触发的是 `opening_pressure` + `maid_warning`——两张卡**无 intent、无对象约束**，是搭任意回合便车的导演节拍卡。模板模式读作"周遭发生的事"，LLM 叙事把它们与玩家行动揉成因果（"找薇拉搭话→侍女塞便签"），且玩家对薇拉的尝试零叙述（事实清单只在**什么都没触发**时标注"无预设事件"）。三个缺口：schema 缺"节拍 vs 回应"的通用区分；上一批校验规则只查"含 custom"漏了"无 intent 约束"这个超集；事实清单缺"玩家行动是否得到专门回应"的归因事实。
4. **头号发现——LLM 路径提议恒为空（C 政策）**：本局 10 个计划的 `proposed_changes` 全部为空，提议机制零使用。后果是公平性反转：菜单交涉会应用 `fallback_proposal`（信任 +1→3→`maid_lends_key` 触发→拿到钥匙），LLM 路径空提议直接透传（不回退 default_proposal，是"阶段 3 LLM 取代它"的设计立场）→ 信任停在 2 → 空手。**同一行动 LLM 路径系统性弱于菜单路径**。root cause 候选：prompt 规则 4"不确定就留空数组"太劝退 + 无示例。这是能力模块设计前必须解决的政策决策。
5. **叙事幻觉（A 表现 / C 修法）**：观察钥匙环的 fail-forward 回合，渲染发明了"摊开手掌"（暗示持有）并把两个场景前的"侧梯/后楼梯"意象贴进当前场景——幻觉散文→玩家误信持有→下轮澄清打脸。事实清单缺行动目标的位置事实，"最近发生"未标注为过去。
6. **custom 撞空无"没有把握"披露（C 披露一致性，小）**：`action.unauthored_attempt` 目前只对 `requires_storylet_match` 意图生效；custom(key_ring) 验证 issues 为空，报价承诺"为后续开门做准备"却无从兑现。
7. **渲染空响应 3/8**：DeepSeek 三个回合返回空文本静默回退模板，且回退提示语（"例如 observe family_portrait"）是写给结构化模式玩家的，对 LLM 模式错位。
8. **多步计划需求首证**："返回走廊，询问侍女"是协议 v0.1 单意图步边界的第一条真实需求证据（按步计价议题的弹药）。
9. **拾取/物品建模实证**：key_ring 不是物品实体（场景对象），且引擎无通用拾取——"不能使用"的澄清是对的，路线图上的物品协议待办获得实证。
