# ISEKAI ZERO 竞品分析与 AIRPG 方向评估

日期：2026-07-14  
状态：产品与架构方向讨论稿

## 0. 执行摘要

ISEKAI ZERO 与 AIRPG 表面上都属于 AI 互动叙事，但两者当前处在不同层次：

- **ISEKAI ZERO 是已经产品化的 AI 角色扮演平台**：重点是跨端聊天体验、多模型、长上下文、消息分支、多媒体生成、创作者发布与商业闭环。
- **AIRPG 是强调可信裁决的互动叙事引擎内核**：重点是结构化状态、感知墙、行动验证、风险报价、原子提交和可审计结果。

AIRPG 的确定性状态、权限分层和原子提交并非错误方向，它们构成了区别于普通 AI Chat 的核心价值。但当前实现把“保护世界一致性”扩张成了“几乎所有有效叙事都必须由作者预先定义”，导致玩家自由输入与有限结果空间之间产生明显冲突：没有命中作者 storylet 的行动，即使合理，也通常只能消耗时间并产生少量软状态变化，无法创造持久的新人物、新地点、新关系、新任务或新局势。

如果产品目标是 30—90 分钟的悬疑密室、剧本杀或解谜关卡，当前模式可以成立；如果目标是几十小时乃至长期运行的宏大故事，当前模式无法通过增加 YAML 和 storylet 规模解决，因为创作者面对的是组合爆炸，而不是简单的内容量不足。

建议的方向不是取消强规则，而是重新划定控制边界：

> 作者定义世界边界、核心事实和剧情锚点；能力模块裁决机械结果；LLM 导演生成锚点之间的局部世界；所有会影响后续玩法的新事实经过结构化验证后再进入权威状态。

这意味着 AIRPG 应从“作者预定义结果，LLM 负责理解和渲染”转向“作者定义边界与引力中心，能力模块负责裁决，LLM 负责生成中间世界”。

## 1. 分析范围与证据边界

本分析基于以下公开材料：

1. ISEKAI ZERO Web 页面及公开发布的 Expo Web JavaScript bundle；
2. ISEKAI ZERO 官方帮助文档；
3. AIRPG 当前仓库代码、README 与设计文档。

需要特别说明：给定聊天地址的数据接口需要登录身份。页面外壳可以访问，但直接请求聊天详情返回未认证，因此本文不分析该聊天的具体内容、提示词或模型输出质量。

本文对外部竞品信息采用三种证据等级：

- **已确认**：公开页面、客户端 bundle 或官方文档直接可见；
- **高概率推断**：可以从公开接口和客户端行为推断，但没有服务端源码证明；
- **无法确认**：后端语言、数据库、任务队列、向量数据库、内部模型编排框架等。

## 2. ISEKAI ZERO 的产品定位

ISEKAI ZERO 的产品中心不是严格意义上的游戏引擎，而是一个“AI RP 内容与创作者平台”。它将以下能力组织在同一个商业闭环内：

- 玩家选择故事、角色 Persona 和 LLM；
- 玩家通过自然语言与故事互动；
- 聊天历史、角色状态和摘要跨会话保存；
- 单条消息可以继续、重做、编辑、删除、保存或创建分支；
- 文本结果可以进一步生成语音、插画、视觉小说、轻小说、漫画和视频场景；
- 创作者可以发布故事和角色，并从付费生成中获得收益；
- 平台以 Mana / Arcane 点数对模型和生成能力进行计费。

它的核心产品策略是尽可能减少内容消费和内容创作之间的边界：创作者提供角色、世界和初始设定，平台通过 LLM 与多媒体模型把它扩展成持续消费的互动内容。

## 3. ISEKAI ZERO 的公开技术形态

### 3.1 客户端与基础设施

| 层次 | 已确认的实现 |
|---|---|
| 跨端客户端 | Expo + React Native Web，同一体系覆盖 Web、iOS 和 Android |
| 路由与 UI | Expo Router、React Navigation、React Native Reanimated、FlashList |
| Web 托管 | 静态前端部署于 Vercel |

| 媒体存储 | S3 与 Google Cloud Storage 风格的对象存储 |
| 监控 | Sentry |
| 支付 | bundle 包含 Stripe、Paddle、RevenueCat 相关集成代码；是否在所有地区同时启用无法确认 |

公开客户端显示出的整体结构大致为：

        │

        │
        ├── 区域化 REST API
        │     ├── 用户与聊天
        │     ├── 消息与分支

        │

客户端中可以确认的部分业务接口包括：

- `chats/{id}/messages`

- `stream/tts`

- `histories/{id}/archive`

- `generate-light-novel`
- `generate-manga`

这些接口说明它采用“服务端保存消息与状态、服务端编排模型、客户端消费流式事件”的形态，而不是浏览器直接调用某个 LLM。

## 4. ISEKAI ZERO 的关键产品机制

### 4.1 Chat-first 的自由角色扮演

ISEKAI ZERO 的默认体验仍然以聊天上下文和提示词为中心。玩家可以选择模型、Prompt Version、输出长度、Temperature、Reasoning、Context Limit 和 Guidance Prompt。创作者和玩家可以通过提示词直接影响模型行为。

这种设计的优势是开放、低创作门槛和快速扩展；代价是普通模式下的世界一致性更依赖模型、上下文和提示词质量。

### 4.2 消息树与分支历史

它把“消息”视为主要产品对象，而不是只保存最终世界状态：

- AI 回复可以有多个 choice；
- 玩家可以重新生成或编辑 AI 回复；
- 可以从任意消息创建新的聊天分支；
- 分支历史可以归档和恢复；
- 消息可以搜索、保存和跳转。

这非常适合以体验和内容消费为中心的 AI RP，但也意味着世界真实性可能依赖当前分支对应的消息历史和摘要。

### 4.3 Chapter / Arc 分层摘要

官方文档描述的长上下文管理至少包含两层：

1. 每 20 条消息生成一个 Chapter 摘要；
2. 每 10 个 Chapter 再压缩为一个 Arc。

用户可以查看、编辑和重新生成摘要。该机制的直接目标是减少上下文 token 和消息费用，同时保留长篇连续性。

这是一种叙事记忆压缩机制，不等于严格的权威世界状态。摘要可能遗漏或误写事实，因此适合保存情节与关系脉络，不适合单独承担物品、资源、位置、承诺和秘密披露等机械事实。

### 4.4 Dungeon Mind

Dungeon Mind 是 ISEKAI ZERO 中最接近 AIRPG 的部分。官方描述将职责分成：

```text
玩家描述行动
→ Story AI 识别需要裁决的行为
→ Dungeon Mind 根据创作者规则掷骰并修改属性
→ Story AI 根据裁决结果写出场景
```

Dungeon Mind 可以维护角色表、HP、MP、属性、技能、物品、状态效果、死亡和升级，并把骰点和状态变化作为透明机械回执展示给玩家。

这说明 ISEKAI ZERO 也已经识别出“故事模型不能同时担任叙事者和最终裁判”的问题。不过 Dungeon Mind 是故事可选模块；AIRPG 则把确定性裁决作为整个引擎的基础原则。

### 4.5 多媒体与商业闭环

ISEKAI ZERO 已经把文字生成扩展成完整的内容消费链：

- Narration / TTS；
- Light Novel；
- Manga；
- Visual Novel；
- 角色与场景图片生成、编辑；
- 视频场景；
- 按模型和 token 计费；
- 免费与付费 credits；
- 创作者收益和推荐分成。

这些能力构成其重要竞争壁垒，但属于平台层，不应与世界引擎内核混为一谈。

## 5. AIRPG 当前形态

AIRPG 当前的目标循环是：

```text
玩家自由输入
→ LLM 生成 ActionPlan
→ 能力路由与状态验证
→ 风险报价
→ 玩家确认
→ 原子提交
→ 世界步进
→ 基于事实清单进行叙事渲染
```

当前已经落地的关键能力包括：

- `ActionPlan → ValidationResult → CommittedOutcome` 的结构化协议；
- 状态 revision 与陈旧计划保护；
- 确定性状态、原子提交和 quote 约束；
- 感知墙，避免秘密通过 UI 或 LLM prompt 泄漏；
- Soft / Mechanical / Canon 等权限分层；
- DeepSeek 理解和叙事渲染；
- YAML 内容、校验器、walkthrough 和 trace；
- 两个小规模样板故事。

尚未形成的平台能力包括：

- Web / 移动客户端；
- 服务端持久化和会话恢复；
- 消息分支与状态分支；
- SSE 流式输出；
- 多模型路由；
- Chapter / Arc 长期记忆；
- 创作者在线编辑与发布；
- 多媒体和商业系统。

## 6. 核心对比

| 维度 | ISEKAI ZERO | AIRPG 当前实现 |
|---|---|---|
| 产品中心 | AI RP 内容平台 | 可信世界裁决内核 |
| 主要数据对象 | 聊天、消息、choice、历史分支 | 状态、计划、验证和提交结果 |
| 默认自由度 | Prompt-first，模型可自由延展故事 | 只有已声明实体、意图和状态路径可产生持久影响 |
| 规则裁决 | 普通故事偏模型；Dungeon Mind 可选 | 确定性裁决是所有故事的基础 |
| 状态安全 | 公开资料无法确认完整边界 | Revision、权限、感知墙、原子提交 |
| 长期记忆 | 完整消息 + Chapter + Arc + 角色状态 | 确定性状态 + 最近事件窗口；暂无摘要层 |
| 未预写行动 | 模型通常可直接延展 | 通常只能产生软代价或无实质进展 |
| 新实体生成 | 支持 AI 生成支援角色和媒体 | 叙事层禁止创造状态中不存在的实体 |
| 分支 | 消息级分支和历史归档 | 暂无状态树和分支快照 |
| 模型 | 多模型、用户可选 | 当前为单一 DeepSeek provider |
| 输出 | SSE 流式生成 | 同步完整响应 |
| 创作方式 | 在线 Creator Studio 和发布平台 | YAML + 校验器 + walkthrough |
| 多媒体 | 语音、图片、视觉小说、漫画、视频 | 纯文本 |
| 商业化 | 点数、支付、收益分成 | 无 |

## 7. AIRPG 当前体验僵硬的根因

### 7.1 玩家输入自由，但结果空间封闭

当前 LLM 可以理解自由文本，却必须把行动映射到当下可用的 capability 和 intent。没有通过静态能力路由的步骤会被判为不可用。

更关键的是，未命中作者 storylet 的行动虽然可以通过 `allow_unauthored` 进入 fail-forward，但其政策是：消耗时间、允许白名单内的 soft patch、不得产生 Mechanical 或 Canon 结果。

因此玩家获得的是“表达自由”，而不是“世界影响自由”。模型能听懂玩家在做什么，却没有权限让合理行动真正改变世界。

相关实现：

- [`capabilities.py`](../server/engine/capabilities.py) 只接受 Soft State 提议；
- [`resolver.py`](../server/engine/resolver.py) 仍以 intent、对象和 storylet 作为主要执行表面；
- [`engine-principles.md`](engine-principles.md) 明确规定未预写尝试只能产生时间与软代价，Canon 不动。

### 7.2 Storylet 实际上仍是行为白名单

项目愿景把 storylet 定义为“因果锚点而不是行为白名单”，但当前运行时中，storylet 同时承担了两个职责：

1. 判断玩家行动有没有有意义的结果；
2. 触发关键剧情效果。

只要第一个职责仍存在，创作者就必须枚举“意图 × 对象 × 条件 × 结果”的组合。故事越大，组合越多；当人物、地点和能力数量增长时，创作成本会迅速失控。

Storylet 应只保留第二个职责：当世界状态达到某个重要条件时，兑现创作者承诺的关键事件。普通行动能否成功，应由通用能力模块判断，而不是由是否存在某张作者事件卡判断。

### 7.3 Canon 被设计成封闭集合

当前权限模型只有两个实际端点：

- 作者和引擎提供的权威事实；
- 不进入状态的表现层文字。

中间缺少“经过验证的生成式事实”。因此 LLM 不能创建之后仍可互动的次要 NPC、临时地点、关系、承诺、任务或局势。

叙事渲染又被要求只能改写事实，不能扩展实体、空间或事件。该约束能够防止幻觉污染状态，但同时把世界变成了预先封闭的对象集合。

### 7.4 世界模拟能力不足以填补锚点之间的空白

当前 world step 主要处理预定义图上的 NPC 移动规则；导演提示也主要从符合条件的 storylet 中派生。尚不存在能够根据人物动机、阵营目标、局势和玩家行为持续提出新世界事件的 LLM Director。

因此“锚点之间由 LLM + 能力模块即兴填充”目前尚未真正落地。

### 7.5 报价机制覆盖面过大时会形成仪式负担

完整的“复述—报价—确认—提交”适合高风险、不可逆或成本显著的行动。如果普通观察、聊天、移动和日常交互也频繁要求确认，系统会不断提醒玩家自己正在操作规则引擎，而不是生活在故事中。

报价机制应该保留，但应从默认交互变成高风险行动的安全带。

## 8. 方向判断：不是取消强控制，而是重划控制边界

### 8.1 必须继续强控制的内容

- 生命、资源、物品、位置和时间；
- 已经提交的世界事实；
- 秘密和信息披露条件；
- 能力、权限与物理边界；
- 不可逆主线变化；
- 创作者声明的禁区和世界法则；
- 玩家不能直接宣布成功或修改数值；
- 所有持久状态变更必须结构化、可验证、可回放。

### 8.2 不应要求作者预写的内容

- 普通对话的逐句回应；
- 次要人物的局部反应；
- 合理的环境细节；
- 过渡地点、路人、商店和旅途事件；
- 锚点之间的连接情节；
- 玩家解决问题的具体手段；
- 次要支线、临时任务和局部冲突。

新的原则应当是：

> 强规则保护世界一致性，不负责限制故事只能沿作者预先踩出的脚印前进。

## 9. 建议的目标架构

### 9.1 创作者从“分支编程者”变成“世界立法者”

创作者应主要提供：

- 世界法则和不可违反的事实；
- 主要地区、阵营、人物和资源；
- 人物动机、关系和长期目标；
- 剧情锚点、伏笔、阶段目标和结局条件；
- 允许生成的地点、人物、事件和物品原型；
- 类型能力模块及其参数；
- 风格、尺度、内容边界和禁区。

创作者不应枚举每个问题的所有解决方法。

### 9.2 Storylet 降级为状态订阅者

普通能力模块负责让行动产生结果：

- 移动模块判断能否到达；
- 社交模块根据动机、关系和筹码裁决；
- 调查模块根据位置、手段和证据层级裁决；
- 战斗模块处理命中、伤害和状态；
- 物品模块处理持有、使用、容器和消耗；
- 经济模块处理购买、交换、雇佣和债务。

Storylet 只订阅状态变化并触发关键锚点。例如，进入档案室可以通过偷钥匙、说服管理员、撬锁、制造事故或寻找其他入口完成；作者只需声明“玩家进入档案室且满足某条件时触发核心发现”，而不是为所有进入方法分别写卡。

### 9.3 引入“生成式局部事实”

建议把事实权限扩展为四层：

| 层级 | 示例 | 处理方式 |
|---|---|---|
| 表现细节 | 天气、杯子颜色、路人的一句闲话 | LLM 可自由生成，不持久化 |
| 生成式局部事实 | 次要 NPC、临时商店、小承诺、局部支线 | LLM 提议，约束检查后持久化 |
| 机械事实 | HP、金钱、物品、位置、关系数值 | 能力模块裁决并提交 |
| 核心 Canon | 世界法则、主线秘密、关键人物身份 | 作者或严格剧情锚点控制 |

当前 `AuthorityLevel` 可以增加类似 `GENERATED_CANON` 或 `LOCAL_CANON` 的层级，并为其设置：

- 生成预算；
- 允许的实体原型；
- 生效范围；
- 生命周期；
- 与核心 Canon 的冲突检查；
- 来源与 provenance；
- 是否允许后续升级为长期事实。

### 9.4 实体晋升

LLM 可以在叙事中自由产生不影响玩法的表现细节；一旦玩家试图与某个细节持续互动，该细节必须晋升为结构化实体。

例如叙事提到“巷子里有一家亮灯的药铺”，玩家只是路过时无需建模；玩家决定进入时，Director 提出：

```json
{
  "type": "location.create",
  "id": "generated_apothecary_17",
  "archetype": "urban_shop",
  "parent_region": "east_district",
  "persistence": "local",
  "constraints": {
    "rare_magic_items": false
  }
}
```

该提议通过世界边界、资源预算和 Canon 冲突检查后进入状态。从此药铺不再是随口描写，而是可以被记住、返回和影响的正式地点。

### 9.5 风险分级，而不是所有行动完整报价

| 风险等级 | 示例 | 交互方式 |
|---|---|---|
| 低风险、可逆 | 普通观察、闲聊、短距离移动 | 自动执行 |
| 有轻微成本 | 买普通物品、花费少量时间 | 显示简短成本后执行 |
| 不确定 | 说服、潜入、追踪、战斗 | 通用检定并展示结果 |
| 高风险、不可逆 | 死亡风险、永久关系破裂、消耗稀有物品 | 完整报价并确认 |
| 违反硬边界 | 凭空修改数值、无能力施法 | 解释原因，不消耗回合 |

### 9.6 新的回合管线

```text
玩家自由输入
→ LLM 识别目标、手段和期望结果
→ 检索当前局部世界、相关长期记忆和能力工具
→ 通用能力模块判断可行性、成本与不确定性
→ 必要时检定或请求澄清
→ LLM Director 提出局部后果、NPC 反应和可选新事实
→ 策略层检查世界边界、生成预算和 Canon 冲突
→ 原子提交机械变化与生成式事实
→ Storylet 根据新状态触发剧情锚点
→ LLM 根据已提交结果叙述
→ 更新结构化状态与分层叙事记忆
```

这个循环仍然保留 AIRPG 最重要的 revision、感知墙、原子提交和 trace，只是不再把“作者是否写过对应 action”作为世界能否产生意义的前提。

### 9.7 双层长期记忆

不建议完全照搬“聊天摘要即记忆”。AIRPG 更适合区分：

```text
权威记忆
位置、物品、资源、关系、承诺、秘密、任务、世界事实
→ 结构化存储，不由摘要覆盖

叙事记忆
对话细节、共同经历、情绪变化、人物表达习惯、阶段情节
→ Chapter / Arc 分层摘要
```

摘要只能帮助模型恢复上下文，不能修改权威状态。

## 10. 建议保留与调整的现有资产

### 10.1 应保留

- `ActionPlan → ValidationResult → CommittedOutcome`；
- 状态 revision 与陈旧计划保护；
- 原子提交和可审计 trace；
- 感知墙；
- 内容与引擎词汇分离；
- 创作者不写代码；
- 高风险报价约束；
- 内容 schema、校验器和 walkthrough 思想。

### 10.2 应调整

- 移除“未命中 storylet 就只能产生软代价”的政策；
- 把 Storylet 从交互白名单改为剧情锚点；
- 允许受约束的生成式局部事实进入状态；
- 将 Canon 从单一等级拆成核心 Canon 与局部生成 Canon；
- 把静态能力路由器发展为真正的通用能力模块；
- 允许叙事生成表现细节，并在需要互动时进行实体晋升；
- 把完整报价限制在高风险和不可逆行为；
- 引入 LLM Director 和 NPC 动机规划，而不仅是确定性移动规则。

### 10.3 两个样板故事的重新定位

当前两个故事更适合作为：

- 状态协议测试夹具；
- 感知墙与原子提交回归用例；
- 能力模块的最小测试场；
- Storylet 锚点机制的验证样本。

它们不应继续承担“证明引擎已经支持自由长篇故事”的任务。下一阶段需要一个专门验证开放性的原型，而不是继续在两个小场景中增加 action 和 storylet。

## 11. 建议验证路线

### 阶段 A：证明不依赖作者 Action 覆盖

制作一个只声明世界、人物动机、物理边界和一个最终锚点的测试场景，刻意不为解决方案编写 action storylet。

玩家应能通过至少五种未预写方法达成目标，且每种方法都能产生：

- 合理的机械成本；
- 持久世界变化；
- NPC 反应；
- 可回放的结构化结果；
- 不违反核心 Canon 的叙事。

### 阶段 B：实现第一个真正通用的能力模块

优先选择社交或调查模块，因为它们最能暴露“模型生成与确定性裁决如何协作”的问题。模块不能依赖任何故事专名，应能在两个现有故事和新开放场景中复用。

### 阶段 C：生成式局部世界

加入：

- 次要 NPC 生成；
- 局部地点生成；
- 实体晋升；
- Local Canon 持久化；
- 生成预算与冲突检查。

### 阶段 D：长篇记忆与状态分支

实现：

- 权威状态快照；
- 事件日志；
- Chapter / Arc 叙事摘要；
- 分支对应独立状态 revision；
- 从任意提交点创建时间线分支。

### 阶段 E：产品化外壳

最后再建设：

- HTTP API 和 SSE；
- Web UI；
- 多模型 provider；
- 在线创作器；
- 多媒体；
- 用户、支付和创作者平台。

## 12. 建议衡量指标

下一阶段不应只统计测试通过数，还应衡量开放性和创作成本：

- **未预写行动有效率**：未命中作者 action 的合理尝试中，有多少产生了持久且有意义的后果；
- **作者覆盖依赖度**：完成一个章节所需的手写 storylet 数量；
- **创作成本**：支持一小时有效游玩需要多少作者配置；
- **状态一致性率**：生成式事实与已有 Canon、位置、物品和时间是否冲突；
- **重复体验率**：不同玩家是否仍被收束到相同几条作者路径；
- **无效回合率**：玩家行动只消耗时间但没有新信息、状态或局势变化的比例；
- **长期召回准确率**：跨 Chapter / Arc 后关键承诺、物品和人物关系是否仍正确；
- **回放确定性**：相同提交日志是否能恢复相同权威状态。

其中最关键的指标是：

> 在作者没有预写解决方案的情况下，引擎能否让合理行动产生可信、持久、可继续互动的后果。

## 13. 不建议直接模仿 ISEKAI ZERO 的部分

ISEKAI ZERO 值得参考的是产品外壳、消息分支、长上下文工具、流式体验和商业闭环，不应直接复制其 Chat-first 的全部假设。

AIRPG 不应放弃：

- 权威世界状态；
- 机械事实与叙事摘要分离；
- LLM 不能直接宣布高权限结果；
- 秘密披露和感知边界；
- 原子提交与审计；
- 内容无关的通用能力协议。

否则项目会失去与普通角色聊天平台之间最重要的差异化。

## 14. 最终结论

ISEKAI ZERO 证明了 AI 互动叙事在产品层需要多端客户端、流式消息、多模型、分支、摘要、多媒体、创作者和计费闭环；Dungeon Mind 又证明了纯 Chat-first 模式在涉及规则、资源和长期状态时需要额外裁判。

AIRPG 已经在确定性裁决、感知墙、状态权限和原子提交上建立了有价值的基础，但当前实现把作者预定义内容放在了过于核心的位置。继续增加 storylet 只能改善两个样板故事，不能自然扩展成长篇世界。

因此建议现在进行架构转向，但不推倒现有内核：

> 保留“LLM 不得绕过规则直接修改世界”，放弃“只有作者预写过的结果才能成为世界事实”。

未来的 AIRPG 应当允许 LLM 在明确边界内创造局部世界，并通过能力模块、生成预算、权限校验和原子提交把合理创造晋升为可持续互动的事实。创作者负责世界的法律、核心人物和剧情引力中心，而不是覆盖所有分支。

只有这样，AIRPG 才能从“规则严谨的小型互动剧本”演进为“能够承载长篇、宏大场景和玩家真正自由选择的生成式角色扮演引擎”。
