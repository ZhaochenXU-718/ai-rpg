# AIRPG 引擎与内容修改守则

日期：2026-07-09

本文档回答一个在阶段 2 试玩中反复出现的问题：

> 遇到体验问题时，应该改内容、改校验器、改引擎，还是留给 LLM？
> 不断修改引擎是否会让它退化成只服务于《午夜前的档案室》的代码？

结论先行：**阶段 2 的多轮真人试玩中，引擎判定核心（resolver / conditions / effects / limits）没有为任何一条体验反馈改过一行**。所有修改都落在内容、校验器、CLI 显示层和协议字段上。这个分层要作为守则维持下去。

## 1. 问题分类法：先问两个问题

拿到一个体验问题，先问：

**问题一：接入 LLM 后它会自然消失吗？**

- 会 → **A 类：表达层问题**。记下来，等阶段 3，不要现在工程化。
- 不会 → 问题二。

**问题二：换一个故事还会发生吗？**

- 不会，只是这个本子的问题 → **B 类：内容问题**。改 YAML；如果是"一类"错误，给校验器加一条规则。
- 会，任何故事都躲不开 → **C 类：协议 / 引擎问题**。这才是动引擎的理由，且必须以通用 schema 字段或通用语义落地。

判断 A 类时要小心一个陷阱：**LLM 能把话说圆，不代表问题消失了**。LLM 只能表达状态里存在的事实；如果事实本身缺失或矛盾（侧门没有铺垫、管家"既在又不在"），LLM 只会把矛盾叙述得更流畅，让玩家更晚才发现不对劲——这比模板文本的干瘪更伤公平感。所以：**状态和事实的问题永远不是 A 类。**

## 2. 修改守则

1. **内容优先。** 能用 YAML 解决的不碰代码。例：大厅意图菜单漏"潜入"、侧门缺空间铺垫、对象缺显示名。
2. **一类 bug 一条校验规则。** 修完具体问题，把它的"类"变成 `validate_content.py` 的自动检查，让下一个故事写不出同样的错。例：场景图连通性、死 flag、转场意图必须出现在触发场景的菜单里。
3. **引擎只为协议缺口而改。** 判据：这个概念是所有故事都需要、而 schema 表达不了的。落地必须是通用字段 / 通用语义，禁止出现指向具体故事的特判。例：在场模型（`available_characters` 即 presence）、对象显示名字段、"每回合最多一次场景切换"。
4. **反向守则：留给 LLM 的不要工程化。** CLI 的"显示名 → ID 别名映射"是这条线的边界——精确匹配可以做，再往下（模糊匹配、同义词、意图猜测）就是在手写一个劣化版理解层，停止。阶段 3 理解层的职责就是把"我看看壁炉上摆着什么"映射成 `observe fireplace`。
5. **CLI 是脚手架，不是产品。** 显示层的修改（面板、提示、别名）可以快糙猛，它们不进入阶段 4 的 Web UI 资产，不值得精雕。
6. **模板模式是显影剂，不是缺陷。** 阶段 2 文本干瘪是预期行为；它的价值恰恰是让状态矛盾无处藏身。判断标准：**状态矛盾必须修，文本干瘪不修。**

## 3. 阶段 2 试玩案例复盘

| 试玩暴露的问题 | 分类 | 处理 |
|---|---|---|
| 玩家输中文人名，引擎要对象 ID | A（理解层） | CLI 做精确别名映射兜底；模糊理解留给阶段 3 |
| 输入接不住却被静默吞掉，玩家整局打空 | C（公平感协议） | 显式警告 + 报价卡提示；"接不住必须显式反馈"进入交互协议 |
| "没有掀起波澜"文本干瘪重复 | A（渲染层） | 按"有无状态变化"分档模板，阶段 3 由 LLM 替换 |
| 大厅菜单没有"潜入"，玩家无法离开 | B + 校验类 | 内容补意图；校验器加"转场意图必须在菜单里"规则 |
| 拿到侧梯线索后不知道能做什么 | C（导演协议） | `transition_options`：前置已满足的转场卡显示为具体导演提示 |
| 状态栏显示全剧本角色，不随场景变化 | C（在场协议） | 状态栏按场景过滤；schema 写明 presence = `available_characters` |
| NPC 状态里的 `location` 是没人维护的死数据 | B（误导性内容） | 删除；schema 禁止无事件卡维护的位置字段 |
| 管家"正在赶来"无法表达，既在又不在 | C（协议缺口，待设计） | 见第 4 节待办；不为管家写特判 |
| 侧门直通档案室缺空间铺垫 | B（内容） | 档案室门口 entry_text 补一句窄门描写，加 `service_door` 对象 |
| 玩家全程不敢用"观察"：目标词表不透明 | B + C | 对象显示名成为协议字段（`id: 标签` 映射）；CLI 裸观察给提示不扣时间 |
| 噪音值无上限反复堆叠 | B（内容，待收口） | 白名单不约束作者事件卡是设计使然；应在内容里限制可重复卡 |

## 4. 待办的协议设计（不急，但别用特判绕过）

- **"逼近中"的在场状态**：二值 presence 表达不了"管家正在赶来"。方向：presence 成为可由事件卡效果改变的状态（如 `butler.present: false` → `butler_catches_player` 置 true），引擎据此过滤在场角色和可选目标。需要 schema 设计，不为单个角色硬编码。
- **对不在场角色行动的约束**：当前可以"威胁"一个还没出现的人。依赖上一条落地后在引擎统一校验。
- **可重复事件卡的效果收口**：`once: false` 的卡反复触发时数值无限堆叠。方向：schema 允许卡声明冷却或效果上限，或在数值路径上声明全局 bound。

## 5. 阶段 3 接入 LLM 时的边界检查清单

- LLM 只承担两件事：**理解**（自然语言 → 意图 + 对象 ID + 白名单 patch 提议 + 输入分类）和**渲染**（判定结果 → 叙事文本）。
- 判定核心（resolver / conditions / effects / limits）接口冻结，LLM 不参与成败判定。
- 渲染 prompt 必须约束：**只能陈述状态与事实清单中存在的东西**，不得发明空间结构、物品或角色行为（侧门教训的反面）。
- 理解层接不住时，沿用阶段 2 的公平感协议：显式告知玩家哪里没接住，而不是猜一个执行。
- 报价的约束力、重报价上限、白名单裁剪在 LLM 路径上原样生效——这套公平感机制本来就是为 LLM 的不确定性准备的。
