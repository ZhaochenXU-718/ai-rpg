# AIRPG 引擎与内容修改守则

日期：2026-07-10

本文档回答一个在阶段 2 试玩中反复出现的问题：

> 遇到体验问题时，应该改内容、改校验器、改引擎，还是留给 LLM？
> 不断修改引擎是否会让它退化成只服务于《午夜前的档案室》的代码？

结论先行：**只有换一个故事仍会出现的协议缺口才允许修改判定核心**。本轮为 resolver 增加的动作原子预检、条件对象和无效动作不计回合，都是跨故事的公平性约束；文件柜、暗格和信任值仍留在内容层。这个分层要作为守则维持下去。

## 1. 问题分类法：先问两个问题

拿到一个体验问题，先问：

**问题一：接入 LLM 后它会自然消失吗？**

- 会 → **A 类：表达层问题**。记下来，等阶段 3，不要现在工程化。
- 不会 → 问题二。

**问题二：换一个故事还会发生吗？**

- 不会，只是这个本子的问题 → **B 类：内容问题**。改 YAML；如果是"一类"错误，给校验器加一条规则。
- 会，任何故事都躲不开 → **C 类：协议 / 引擎问题**。这才是动引擎的理由，且必须以通用 schema 字段或通用语义落地。

判断 A 类时要小心一个陷阱：**LLM 能把话说圆，不代表问题消失了**。LLM 只能表达状态里存在的事实；如果事实本身缺失或矛盾（侧门没有铺垫、管家"既在又不在"），LLM 只会把矛盾叙述得更流畅，让玩家更晚才发现不对劲——这比模板文本的干瘪更伤公平感。所以：**状态和事实的问题永远不是 A 类。**

## 2. 修改守则

1. **内容优先。** 能用 YAML 解决的不碰代码。例：大厅意图菜单漏"潜入"、侧门缺空间铺垫、对象缺显示名。
2. **一类 bug 一条校验规则。** 修完具体问题，把它的"类"变成 `validate_content.py` 的自动检查，让下一个故事写不出同样的错。例：场景图连通性、死 flag、转场意图必须出现在触发场景的菜单里。
3. **引擎只为协议缺口而改。** 判据：这个概念是所有故事都需要、而 schema 表达不了的。落地必须是通用字段 / 通用语义，禁止出现指向具体故事的特判。例：世界图、实体位置、对象显示名字段、"每回合最多一次玩家移动"。
4. **引擎代码不认识故事专名。** 空间系统只认识 entity、node、edge、position 和 movement rule；角色动机与具体路线全部留在内容 YAML。新增能力若只能用某个角色或场景解释，就还没有抽象完成。
5. **反向守则：留给 LLM 的不要工程化。** CLI 的"显示名 → ID 别名映射"是这条线的边界——精确匹配可以做，再往下（模糊匹配、同义词、意图猜测）就是在手写一个劣化版理解层，停止。阶段 3 理解层的职责就是把"我看看壁炉上摆着什么"映射成 `observe fireplace`。
6. **CLI 是脚手架，不是产品。** 显示层的修改（面板、提示、别名）可以快糙猛，它们不进入阶段 4 的 Web UI 资产，不值得精雕。
7. **模板模式是显影剂，不是缺陷。** 阶段 2 文本干瘪是预期行为；它的价值恰恰是让状态矛盾无处藏身。判断标准：**状态矛盾必须修，文本干瘪不修。**

## 3. 阶段 2 试玩案例复盘

| 试玩暴露的问题 | 分类 | 处理 |
|---|---|---|
| 玩家输中文人名，引擎要对象 ID | A（理解层） | CLI 做精确别名映射兜底；模糊理解留给阶段 3 |
| 输入接不住却被静默吞掉，玩家整局打空 | C（公平感协议） | 显式警告 + 报价卡提示；"接不住必须显式反馈"进入交互协议 |
| "没有掀起波澜"文本干瘪重复 | A（渲染层） | 按"有无状态变化"分档模板，阶段 3 由 LLM 替换 |
| 大厅菜单没有"潜入"，玩家无法离开 | B + 校验类 | 内容补意图；校验器加"转场意图必须在菜单里"规则 |
| 拿到侧梯线索后不知道能做什么 | C（导演协议） | `transition_options`：前置已满足的转场卡显示为具体导演提示 |
| 状态栏显示全剧本角色，不随场景变化 | C（在场协议） | schema v2 以 `positions` 为唯一位置源，UI 按与玩家同节点派生 presence |
| NPC 状态里的静态 `location` 是没人维护的死数据 | B + C | 升级为由 world step 和 `move_entities` 维护的通用位置状态，不再由场景复制名单 |
| 管家"正在赶来"无法表达，既在又不在 | C（协议缺口，已解决） | 抽象世界图 + `move.toward` + `phase: after_world`；实现不含管家特判 |
| 钥匙已获得但看不见、只能隐式生效 | C（物品协议，已解决） | `items` + 唯一 `item_locations` + 派生口袋 + 显式 `use` |
| 进入关键区域后无法返回 | C + B（移动协议与内容） | 通用 `scenes.exits` + `engine_action: move`；具体可返回边由故事声明 |
| 无首选道具进入档案室后必败 | B + 回归类 | 内容增加有代价替代解，并用“无徽章路线” walkthrough 防止软锁复发 |
| 线索要求对暗格用钥匙，触发器却要求文件柜 | B（内容） | 统一规范交互对象；walkthrough 按玩家实际看到的目标回归 |
| 未发现的暗格提前出现在对象面板 | C（感知协议）+ B | `visible_when` / `actionable_when` 通用对象条件；内容声明发现条件 |
| 无匹配的“使用/潜入”仍扣时推进世界 | C（动作原子性） | `requires_storylet_match`；报价前验证，失败不扣时、不计回合、不推进 world step |
| 参数不足的错误被普通失败文案吞掉 | C（反馈协议） | Session 在计回合前校验；renderer 显示 errors；日志记录 errors |
| 报价只写通用 patch，漏掉确定性事件效果 | C（报价约束） | 在私有副本预演完整确定性回合，分开展示固定代价和预计影响 |
| 全量预演直接上报价卡，执行前剧透结局与暗格 | C（感知协议） | 感知墙（`perception.py` + 内容 `perception` 块）：报价卡只披露玩家已可感知的公开状态变化，全量预演仅供约束力校验与日志 |
| 报价提议规则、风险阈值、状态栏标签硬编码悬疑词汇 | C（守则 #4 违例） | `fallback_proposal` / `quote_warnings` / `perception` 全部下放到故事 YAML，引擎只认识形状不认识词汇 |
| 侧门直通档案室缺空间铺垫 | B（内容） | 档案室门口 entry_text 补一句窄门描写，加 `service_door` 对象 |
| 玩家全程不敢用"观察"：目标词表不透明 | B + C | 对象显示名成为协议字段（`id: 标签` 映射）；CLI 裸观察给提示不扣时间 |
| 噪音值无上限反复堆叠 | B（内容，待收口） | 白名单不约束作者事件卡是设计使然；应在内容里限制可重复卡 |
| LLM 路径继承阶段 2 严格模式：合理但未预写的尝试被免费拒绝，且可零成本探测作者面 | C（判定政策） | `allow_unauthored`：LLM 计划的未预写尝试变为扣时 fail-forward 回合（软代价照裁剪、canon 不动）；结构化无 LLM 路径保持严格 |
| 澄清问答跨输入不连续，玩家的"是的用它"靠运气被理解 | C（理解协议） | session 持有未决澄清，下一次自由输入作为回答注入 PlanRequest（复用 revision/parent 链），提交后清除 |
| 判定结果与拒绝原因是引擎错误码直出，破坏沉浸 | A（渲染层，已解决） | LLM 渲染层（`narration.py`）：事实清单在感知墙内组装，prose 只能改写事实不能扩展事实；失败静默回退模板；机械行恒显示作为公平回执 |
| "和薇拉聊遗嘱"把玩家送出了大厅：转场卡用裸 custom 触发 | B + 校验类 | LLM 时代 custom 承载一切自由文本，重效果卡必须带对象约束；三张转场卡补 `object_any`；校验器新规则：custom 触发 + 重效果 + 无对象约束 → 警告 |
| 报价没披露"你将离开大厅"，确认后才发现自己移动了 | C（报价约束） | 感知墙开一个例外：玩家**自身**的移动是自己行动的一等后果不是隐藏世界事实，报价卡显示"预计移动：A → B" |

## 4. 后续协议待办（继续禁止特判）

- **感知层**：v2 已解决物理位置、在场和状态条件对象；相邻可听见、遮挡、远程通信仍应作为位置之上的通用派生关系设计。
- **容器与物品细节**：唯一物品位置、背包和对象可见性已经落地；后续再设计通用拾取、打开容器、堆叠数量、耐久与消耗流程。
- **可重复事件卡的效果收口**：`once: false` 的卡反复触发时数值无限堆叠。方向：schema 允许卡声明冷却或效果上限，或在数值路径上声明全局 bound。

## 5. 阶段 3 接入 LLM 时的边界检查清单

已落地的两道结构性门（2026-07-12）：

- **感知墙**（`server/engine/perception.py`）：`PlayerPerception` 是 LLM 理解层的唯一输入，报价卡与状态栏的唯一披露依据。不在感知里的事实，结构上进不了 prompt 和 UI。
- **静态能力路由器**（`server/engine/capabilities.py`）：ActionPlan 只有经 `validate_plan` 产出的执行载荷才能到达 resolver；soft 提议过白名单裁剪，canon/mechanical 提议剥离，无效计划不扣时、不计回合。v0.1 承兑范围见 `docs/llm-action-plan-protocol.md` 10.1。

其余边界不变：

- LLM 只承担理解、规划与渲染，判定核心（resolver / conditions / effects / limits / world）接口冻结，LLM 不参与成败判定。fail-forward 政策（`allow_unauthored`）没有破例：LLM 的未预写尝试仍然只能"消耗时间 + 白名单软代价 + 零 canon 效果"，成败仍由引擎判。
- 渲染 prompt 必须约束：**只能陈述状态与事实清单中存在的东西**，不得发明空间结构、物品或角色行为（侧门教训的反面）。已由 `narration.py` 落地：事实清单是渲染 LLM 的全部世界；无事件回合明确标注"不得虚构成功"。
- 理解层接不住时，沿用阶段 2 的公平感协议：显式告知玩家哪里没接住，而不是猜一个执行。
- 报价的约束力、重报价上限、白名单裁剪在 LLM 路径上原样生效——这套公平感机制本来就是为 LLM 的不确定性准备的。
